<Callout type="info">
Synchronous vs asynchronous is about waiting. Blocking vs non-blocking is about whether the current execution thread is forced to stop.
</Callout>

## The key question

> After starting work, can the caller keep doing useful work before the result is ready?

If no, the call is synchronous from the caller's point of view. If yes, it is asynchronous.

## Synchronous I/O

The caller starts an operation and waits until it finishes.

```typescript
import fs from "node:fs";

doWork();
const content = fs.readFileSync("file.txt", "utf8");
doMoreWork(content);
```

## Asynchronous I/O

The caller starts an operation, registers interest in the result, and continues.

```typescript
import { readFile } from "node:fs/promises";

async function main() {
  doWork();
  const promise = readFile("largefile.dat", "utf8");
  doOtherWork();
  const content = await promise;
  doMoreWork(content);
}
```

## Four words people mix up

| Term | Meaning |
|---|---|
| Synchronous | Caller waits for completion before continuing. |
| Asynchronous | Caller can continue before completion. |
| Blocking | Current thread cannot proceed. |
| Non-blocking | Operation returns immediately if it cannot progress now. |

They are related, but not identical. A system can expose async APIs while internally using blocking worker threads.

## Async workload patterns

- Queue a background job and return `jobId`.
- Write to a log/topic and let consumers process later.
- Use async replication, where follower state lags leader state.
- Use async database commit modes when durability/latency tradeoffs are acceptable, such as PostgreSQL asynchronous commit ([PostgreSQL docs](https://www.postgresql.org/docs/current/wal-async-commit.html)).
- Use OS readiness APIs such as `epoll` on Linux ([man page](https://man7.org/linux/man-pages/man7/epoll.7.html)) or newer interfaces like `io_uring` ([man page](https://man7.org/linux/man-pages/man7/io_uring.7.html)).

## Pros and cons

| Synchronous | Asynchronous |
|---|---|
| Easier mental model. | Better resource utilization. |
| Simple error propagation. | More states: queued, running, done, failed. |
| Good for quick operations. | Better for slow I/O and background work. |
| Can waste time waiting. | Harder retries, ordering, observability. |
